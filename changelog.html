Changelog

Every release, newest first. Security marks what every device should get at once. A Major update (in bold at the start of an entry, and in the file MAJOR of the repository) changes how a session connects or runs: a device with a management folder installs it only once the manager released it, one without asks on its screen. Downloads and signed update packages: releases.

0.3.2 (2026-11-08)

  • A computer on another port (#182): the remote computer (or broker) takes name:port, as its help text said, for a PC or VM reached through port forwarding. Before, Save refused it with "Invalid broker", also in Workgroup mode where there is no broker. The fallback brokers and the other computers of the sign-in screen take the same form. Diagnostics and the hardware test try each computer on its own port, and after a drop the VM is asked on the port of the session.
  • 4K and other large screens (#183): a Screen section in the settings.
    • Resolution: native, or one of the modes the monitor offers (DISPLAY_RESOLUTION).
    • Scale: automatic (200% on a 4K monitor, 100% otherwise) or 100-200% (DISPLAY_SCALE), for the screens of the device, the web page and the remote desktop, which Windows gets as its own display scale.
    • Monitors (MULTIMON), until now only in the manager.
    • Applied when saved, no restart. 125-175% are drawn sharp, not blown up.
  • The manager 1.1.6 sets both for the whole site, a group or one device, and takes name:port too.

0.3.1 (2026-11-01)

  • A lighter image: what only some devices use is installed where it is used, the first time (Internet needed then; on a live stick with its settings partition it stays on the stick). About 430 MB less on every device that does not use it:
    • No browser in the image. A device gets one only when its settings have a web page (web button or kiosk page), and only the one chosen: Chromium, or Firefox ESR, Brave, Chrome, Edge (Chromium is then removed). No web page: no browser at all, also on the devices that had one.
    • Tailscale: installed when turned on, kept up to date with the security updates, removed with its repository when turned off (signing in again is then needed). In 0.3.0 a device updated from an older version had none.
    • Bluetooth: the first time the Bluetooth page is opened. Smart cards (pcscd and its drivers): when a reader is first plugged in; sessions open as before without them. WireGuard, OpenVPN: when that VPN is chosen.
    • Devices already installed keep what they have (but the browsers, as above).
    • INCLUDE_BROWSER=yes in build.conf keeps Chromium in an image of your own, for devices that never reach the Internet.

0.3.0 (2026-11-01)

  • Domain or workgroup (#174): the first start asks for the environment of the device, Active Directory domain (brokers, collections, central management) or Workgroup (one computer or virtual machine, a local or Microsoft account), and the settings show only what applies (SETUP). Devices already set up keep what they have: the environment is inferred from their settings.
  • Password remembered (REMEMBER_PASSWORD): the password of the default user stays on the device, sealed in the TPM when there is one; at power on the desktop opens by itself. Removed as soon as Windows rejects it.
  • Wake-on-LAN of the remote computer: its MAC address is learnt after the first connection (or set in WAKE_MAC); a computer that does not answer is woken up, with a wait screen (WAKE_WAIT).
  • Computers found on the network: in a workgroup, the computer field offers the computers of the network with Remote Desktop on. Several computers (CONNECTIONS): the sign-in screen offers the choice.
  • Tailscale (VPN=tailscale): the computer at home reached from outside, no server to set up; the device shows a sign-in link to open on a phone.
  • Bluetooth: headsets, keyboards and mice paired from the settings of the device; audio through PipeWire.
  • The browser of your choice (BROWSER, #133): Chromium, Firefox ESR, Brave, Google Chrome or Microsoft Edge, installed only on the devices that choose it, from its maker's signed repository, kept up to date with the security updates, with the same rules for all of them.
  • The live system keeps its settings (LIVE_PERSISTENCE): started from a USB stick with free space, it makes a partition there at the first start; from the next start settings, updates and Wi-Fi stay, as on other live distributions. A stick written with an older image gets there with this update, without writing it again: the update changes its partition table (nothing of the image moves, BIOS and UEFI start as before), the settings partition is made at the next start and used from the one after. The image is now laid out as Debian's own (an MBR, the image mountable from partition 1, the EFI partition after it): the old layout let live-boot mount only the whole stick, and then no partition of it could be used.
  • Install alongside Windows: a new entry of the installer uses the free space of the disk (shrink Windows first) and leaves Windows and its partitions as they are; the boot menu offers both (OpenThinRDP first, 5 seconds). The installer asks which way to partition with "the largest continuous free space" already chosen, then shows the partitions it is going to make and asks before writing, as before.
  • Help for Microsoft accounts: in a workgroup a refused password says that the account's email address and password are needed, the Windows Hello PIN is not accepted by Remote Desktop.
  • The hardware test of the live system shows once per stick that keeps its settings, not at every start.
  • The ISO of this release is needed only for a new stick or an install: a stick in use gets everything with the update, the settings partition included.

0.2.28 (2026-10-28)

  • The manager has releases of its own, from 1.0.0: numbered apart from the devices, on its repository, signed with the same project key. This release carries one last manager (0.2.28): it updates itself to the releases of the manager, and from there to 1.0.0, by itself. From the next release of the devices on, their release no longer carries the manager.
  • What manager 1.0.0 brings: the Health Center no longer stays empty when a number goes down very slowly (the days until it ran out were too many for the reading, and nothing was shown, not even the last reading); the last reading at once when it opens, then the new one part by part, with its progress in Home too; no long .NET error when the window closes after Update the manager; an error nobody caught is written to %LOCALAPPDATA%\OpenThinRDP\manager-errors.log and said in a few words. The servers, the iDRACs and the rest are read at the same time, the iDRACs with one session each (a reading of a whole site went from 3 minutes to under one), and the progress moves part by part.
  • Anonymous counts, one per device: the counter tells visitors apart by internet address and program, so the devices of a site, all behind one address, counted as one (7 devices sent, 1 counted). Each send now carries a random number made for that send only, kept nowhere and taken from nothing of the device (privacy). The manager sends once a day instead of once a week.

0.2.27 (2026-10-28)

  • The anonymous counts get out (#167): a device started them in the background of its report, which runs as a oneshot service, and systemd stopped them when the report ended, before anything was sent, on every device. They now run in a unit of their own (systemd-run): seen on an OptiPlex 3000 Thin Client, they reach the counter within a minute. What is sent does not change (privacy), and ANON_STATS=off still turns them off.
  • Manager: no more -EncodedCommand: the launcher started Windows PowerShell with the manager as a Base64 command line, which EDRs such as SentinelOne report as suspicious. It now starts OpenThinRDP-Manager.start.ps1, a fixed script of a few lines signed with the release, and hands it the manager on its standard input: nothing of the manager goes on a command line or to the disk. After the update the manager starts once more through the launcher of before; from the next start on, through the new one.
  • Manager: the site key reaches every device by itself: a device that was off when the site key was sent, or was installed again, took no update from the folder any more (UPDATE_KEY=site: "invalid signature"). The manager, open with the vault, now sends the key to such a device as soon as it is on (SSH), and notes it in changes.log.
  • Manager: it opens again after updating itself: after an update of 0.2.24-0.2.26 it could close instead of starting again (the new start found the one still closing and gave way to it). It now waits for it.

0.2.26 (2026-10-26)

  • Webcams that keep up (#165): a webcam that compresses to H.264 by itself sent that H.264 to Windows as it was, and those frames cannot be dropped: a late one held the next and the picture fell behind. The webcam is now read in MJPEG and encoded by the device, which drops a late frame and keeps up, on the video engine of the processor (Intel Quick Sync, VA-API) so the processor stays free: 30 fps at 1080p on an OptiPlex 3000 Thin Client, the processor 89% idle. And Windows is offered at most 1080p (720p on a device without such a video engine), where it picked the largest a 2K webcam had. Three settings change it: CAMERA_H264, CAMERA_HWACCEL, CAMERA_MAX, in the manager too.
  • FreeRDP fb0198dbe: the options of the camera channel (h264, hwaccel, maxres), built with VA-API.
  • Tip: in a dark room many webcams lengthen their exposure and give half the frames (10 fps instead of 20-30). More light, or a webcam with a fixed frame rate, helps more than any setting.

0.2.25 (2026-10-26)

  • The manager is signed with Authenticode: OpenThinRDP-Manager.exe carries the signature of the project (CN=OpenThinRDP Project, with a timestamp). An EDR or antivirus that held the manager back (SentinelOne, #133) is told once to allow it by signer, and every next release passes: how. Your own code signing certificate still works too (Settings > Security > Code signing).
  • The right time after the change of the clock: Windows takes the time zone of the device only when a session opens, so a session open across the change to or from daylight saving time showed the time one hour off until it was opened again. The device now opens it again by itself when the clock changes: a few seconds, the programs stay open.
  • A new release is said where you look: Home lists New version for the devices (or of the manager) with what the folder publishes now, and the menu counts it on Updates. In 0.2.24 the window checked GitHub but showed it nowhere.
  • Readings that end: the iDRACs are read in parallel, firmware, memory modules and processors only every 6 hours, and the next reading starts 3 minutes after the end of the last one (a reading longer than 3 minutes ran back to back). Each step and each part of a controller keeps how long it took.
  • Rings in proportion: memory, disks and the other rings of the manager were drawn full or empty, never in between.
  • A narrow window puts the cards of a row two by two, then one under the other, instead of a scroll to the side.
  • Charts keep their words straight (they were stretched with the drawing), the days of the scheduled jobs come in the language of the manager, and the hints that still named the settings of 0.2.23 lead to the line of the server.

0.2.24 (2026-10-26)

  • A new window for the manager: every page and every dialog drawn on the WebView2 of Windows (the installer of Microsoft comes with the manager when a PC lacks it). Columns you can widen and sort, filters, a right click menu on each line, a page that stays as you left it when you come back, one copy open at a time, and a start in a fraction of a second.
  • Settings in one place: Site first (time zone, language and keyboard of all the devices, language of the manager), then Infrastructure and servers, where each iDRAC, Proxmox, vCenter or Veeam server has its own account and a Test button that says in plain words what is wrong. No setting is written in two places any more.
  • The hardware of the servers as the iDRAC shows it: what the iDRAC says of each part (processors, memory, disks and RAID, power supplies, fans, temperatures, voltages, batteries, chassis intrusion, licences, log), then every disk with its remaining life and predicted failure, RAID volumes and the controller battery, memory module by module, processors, network ports, temperatures with their thresholds, the hardware log of 30 days and every firmware version. One line per server in Home.
  • Ignore a notice for a while, or until you restore it, with a note of why; it comes back by itself if it gets worse.
  • Who opens the manager: personal access with the Windows account (a user or an AD group, at their level), the access code kept for emergencies.
  • A USB device as a drive, also when the others go whole: USB_LOCAL (VID:PID) keeps it on the device in every mode, its storage a drive in Windows; the manager sets it, or USB_REDIRECT, from the peripherals of a device, for that device, its group or all, and plugs a device in again from there.
  • The time zone from a list in the settings of the device: every zone of tzdata, with a search while typing ("rome" finds Europe/Rome) instead of the exact name to type (#154).
  • Anonymous counts from the devices really leave now: they were sent with curl, which is not in the image, so no device ever sent one; now python3, already in the image, sends them. A new device sends its first counts with its own settings, before it takes the central ones; ANON_STATS=off in the central settings holds from then on, also after an update (privacy).

0.2.23 (2026-10-25)

  • The manager is a project of its own: openthinrdp-manager, free for any use, also commercial, and closed from this release. What it runs on your servers stays readable (commands\, rds\), and it shows what it will do before you confirm. The manager of the releases up to 0.2.22 stays under the GNU GPL. The thin client does not change: GPLv3, open.
  • It works without devices too: the first start offers the servers alone, a Health Center for Hyper-V, clusters, Remote Desktop, SQL and backups.
  • A new Home: the infrastructure, the devices, one list of what to look at, the sign-ins of today in their phases, the jobs of today, 30 days of memory with a forecast. It shows the last reading of your PC at once, with its time, while the new one comes (the infrastructure takes about half a minute).
  • Experience: how long each sign-in takes (broker, VM, Windows), the latency of the sessions, dropped and frozen ones, per user and device, kept 40 days. Tell your users: see privacy.
  • Scheduled jobs: restart, switch off, a message or an update, once, daily or weekly, on devices or groups; each device reports how it went.
  • Certificates and the enterprise CA: every certificate of every server on its page (what uses it, when it expires, whether it renews by itself), the CA and its revocation list, and which RDP servers present a certificate a device could verify. Security > Enterprise CA requests the signing certificate of the manager from your CA and follows its renewals, sends the CA to the devices, which trust it from their next report, and gives the desktops their RDP certificate from your CA (a template and the GPO, renewed by themselves): the way to RDP_CERT=verify, the pilot groups first.
  • Not only Hyper-V: Proxmox VE, VMware vSphere, Veeam Backup & Replication and Citrix Virtual Apps and Desktops in the Health Center, each from its own API, read only; the hardware of HPE iLO, Lenovo XClarity and Supermicro too.
  • Peripherals and inventory: model, serial number, BIOS and the USB devices of each device; a required peripheral that is gone is shown to look at. Rules per group, an inventory to export, a status page in HTML.
  • Health Center: maintenance per item, notices when a problem comes or goes, history and forecast, the services as their users reach them, leftovers, a baseline to come back to, iDRAC (power, supplies, temperatures), custom checks and commands, backup of the VMs to a share (a Linux VM is copied with its memory), the witness and the FSMO roles, administration without administrator rights (JEA), and -HealthReport -Json for Task Scheduler.
  • The manager starts at once: its launcher draws the access window in a fraction of a second while the manager loads behind it; the menu and the titles come first, each page whole after. OpenThinRDP-Manager.cmd and .vbs go: start OpenThinRDP-Manager.exe (-Install for a shortcut on each PC).
  • The manager refuses changed files: the files of a release are signed (MANIFEST.txt, the project key); a file changed, missing or added stops the start with their list.
  • Remote screen with consent: REMOTE_CONSENT=ask asks the user of the device before the screen is shared.
  • Note: Microsoft Defender with old signatures may hold the manager back; update its signatures.

0.2.22 (2026-10-23)

  • Diagnostics of a device in one file: the events, the log of the last session and of the frozen ones, the journal, the kernel, the update logs, the network, the hardware and the settings without their secrets. From the manager (Collect its diagnostics, then Open its diagnostics, with a GitHub issue only if you want), from the diagnostics screen of the device (Send to the administrator), or by itself after a frozen session or a power off in a session. It lands in diag\ of the management folder; nothing goes to the project unless you send it.

0.2.21 (2026-10-23)

  • Major updates go through the manager: we mark in the release the ones that change how a session connects or runs. A device with a management folder installs one only once the manager released it to that device, after a second confirmation, also when it updates straight from GitHub. The first major update marked this way comes later: 0.2.21 itself is not one.
  • The update question only without a management folder: the live system from the USB stick, or an image of its own with site.conf only, asks every new version at the sign-in, with its changes. A normal update installs after 30 seconds without an answer, a major one only with a yes; Not now lasts until the next start. Installed and managed devices update as the site says, without a question.
  • Pilot devices are a group: Release from GitHub sends a new version to all devices or to the groups ticked.
  • The manager starts in under 2 seconds instead of about 9: the other pages are built right after the window shows.
  • The manager updates itself (on by default, Updates > This manager) when nothing is being edited, and starts again with the vault still open.

0.2.20 (2026-10-23)

  • A major update asks once more: a release marked Test first changes how a session connects or runs. The manager says so above the notes, proposes the pilot devices first, and before it goes to all devices it asks once more, with No as the default answer.
  • A release to the groups you choose: Release from GitHub can send the new version to the groups ticked in a list (one or more, with the pilot devices); every other device stays on the version it has. The manager now also reads the version of a group and of the devices inside groups.
  • The manager accepts a session collection with spaces: tsv://MS Terminal Services Plugin.1.<collection> was refused with RDS collection not valid, although the devices take it since 0.2.2. The manager now uses the same rule as the devices, and a test keeps the two equal.

0.2.19 (2026-10-23)

  • The time zone of the device: TIMEZONE=Europe/Amsterdam (any zone, in the settings of the device, centrally or in the manager). The published ISO runs on UTC, so outside the UTC zone the clock, the power schedule and the time zone of the session were off by hours until now. Empty keeps the one of the image.

0.2.18 (2026-10-23)

  • Test first. A session whose UDP transport stalls comes back by itself: seen twice in a video call, the pointer moved but the picture, the camera and the microphone stayed stuck until the device was switched off, while the server sent nothing for hours. When FreeRDP keeps sending over UDP and nothing comes back for 60 seconds, the session is closed and reopened over TCP until the device restarts (TRANSPORT=auto); what FreeRDP was doing goes to session-hang.log. An idle session is never taken for one.
  • The log of the last session survives a power off: the FreeRDP log (in memory) is kept at shutdown as /var/log/openthinrdp/last-session.log. A device switched off during a session says so in its events, with the threads of FreeRDP in session-hang.log. Both, and a stalled UDP transport, are in the anonymous counts.
  • A reinstalled device: its new SSH key is confirmed from any command: Restart, Update and the other device commands now ask whether to accept the new host key, as the remote screen did, instead of showing the ssh warning.

0.2.17 (2026-10-23)

  • The anonymous counts say what went wrong: frozen and dropped sessions (with the exit code of FreeRDP), connections that failed or timed out, failed updates, programs that crashed, graphics hangs, kernel errors and stops without a shutdown, counted since the last send, by version and by model. Only the kind, a code number and the name of a program leave the device, never the text of a message. docs/privacy.md lists them.

0.2.16 (2026-10-23)

  • The network on the sign-in screen, and a Wi-Fi page: a small sign at the top right shows Wi-Fi with its signal, cable or no network, and the address. With the PIN of the settings it opens a page that lists the Wi-Fi networks in range: pick one, type the password, and the page says whether it joined, with its address and whether the management folder answers. A wrong password changes nothing: it is tried apart first, and the Wi-Fi of before comes back by itself. Also from the settings (Wi-Fi networks…).
  • Anonymous counts for the project, on by default: the model of the computer, its processor and memory, the versions and a few yes/no, at the first start and then once a week; the manager its version, Windows and how many devices, in ranges. Never names, addresses or users. Off with ANON_STATS=off (the last setting of a device, or centrally) and in Settings > Manager. Everything sent is listed in docs/privacy.md.
  • Room for a failure counted on the memory a VM needs to restart: a VM with dynamic memory restarts on another node with its startup memory, not with what it grew to during the day. 123 GB of memory in use were 114 GB to restart, and a node with 121 GB free was reported as too small.

0.2.15 (2026-10-22)

  • Two more commands for a device in the manager: Force update (looks for an update at once, also past the 3-hour pause of GitHub; an open session stays open) and Disconnect the session (its desktop stays open, the device goes back to the sign-in and does not reconnect; the device needs 0.2.15).
  • A restart or power off that did not reach the device says so: they run 2 seconds later on the device, so the command answers before the connection drops. A failed connection used to count as done (restarting, with nothing sent).

0.2.14 (2026-10-22)

  • How many updates, on Updates in the menu: a number instead of a dot, one for the devices (a release on GitHub newer than the one published to them) and one for the manager; the tooltip says which.

0.2.13 (2026-10-22)

  • A connection can always be left: Cancel on the connecting screen ends the attempt and goes back to the sign-in; with no desktop after 150 seconds the attempt ends by itself and says so; a FreeRDP stopped by the system for 10 seconds is ended too. FreeRDP runs without a console: missing a user it can no longer wait forever for an answer nobody can give (a till stuck on connecting until switched off).
  • Never a sign-in without a user: an empty field is the default user as it is at that moment, and without one the name is asked. The sign-in screen is drawn again when the settings change (a default user or the kiosk mode that arrived a second after the screen).
  • A device keeps its last settings when its file is not in the folder (moved by hand, a group its version did not know): before, its own settings went back to the defaults. Remove all exceptions in the manager now leaves an empty file, which is what says no exceptions.

0.2.12 (2026-10-22)

  • New versions in sight, with what they change: an orange dot on Updates in the menu and on Release from GitHub when GitHub has a release newer than the one published to the devices (and on Updates for a newer manager); the Updates page says which version GitHub has. Before Release from GitHub and Update the manager a window shows the notes of every version in between, then asks. The check runs at the start and every 6 hours.
  • The Health Center reads in 25 seconds instead of 60: the hosts, the domain controllers and the other servers are asked together, and SQL Server is read while they answer. The same checks with the same results (compared check by check on a real site).
  • Leftovers of earlier versions removed from the manager: 44 texts no window used any more, a function never called, a settings tab built and never shown, values assigned and never read.
  • A fault that is over gives no warning any more: critical events and errors of the RDVH agent warn only while they go on (the last one within the hour); a broker silent for more than an hour is the row of a broker that is gone, not a third broker. A file share witness down for five hours had kept four servers yellow for the next 24.

0.2.11 (2026-10-21)

  • Health Center settings by area: general, Hyper-V and cluster, domain and DNS, remote desktops, SQL Server, file and other servers, devices and appliances, backup. Each area has its switch, the servers it reads (one line each, with a remove button and + Add, instead of a small grid), its own settings, its thresholds as numbers with their names (no more DiskPct=10; ... to type) and its checks; the list on the left says which areas are on and how many of their checks. An area switched on without what it needs (a host, a domain controller, a broker...) is not saved: the window goes there and says what is missing. An area never configured opens switched off.
  • Save in the Health Center settings saved nothing: the buttons were created twice, and the Save in front had no action.
  • A frozen session reconnects by itself: a FreeRDP still connected but no longer reading (data waiting in its sockets, the queue never shrinking for 60 s) is killed and the session reopened, like after any drop. Seen during a call with microphone and camera: the screen stayed frozen for hours until the device was switched off. What it was doing (its sockets, its threads, the end of its log) is kept in /var/log/openthinrdp/session-hang.log.
  • 10 000 lines a day less in the journal: the kiosk no longer asks systemd every 5 s about the collected update unit ("Failed to open /run/systemd/transient/openthinrdp-update.service").
  • A device before 0.2.9 is not moved into a group: it looks for its file only in config\, so in a group it lost the settings of its own (they went back to the defaults). The manager now refuses the move and says to update the device first.

0.2.10 (2026-10-21)

  • An address for every device that is on the network: when its main adapter has no IPv4, a device reports the address and adapter of its default route instead of IP=none; and for a report without an address the manager looks the name of the device up in the DNS before saying it has none (remote screen, power and commands) (#80).
  • The age of a device right in every time zone: devices write the time of their report in UTC too (UPDATED_UTC), and the manager uses it. The ISO is built with Etc/UTC: a manager two hours east of UTC saw every device two hours old, as off or offline (#80).
  • The actions of a device on a line of their own, with their names: remote screen, power and commands, version, group, logo. They used to be bare icons in the top right corner and, on a small screen, covered the state of the device. Past two lines only the secondary ones keep just their icon.
  • A narrow window works: the column of the pages keeps only its icons under 1200 points, the group links sit under the count instead of over it, the note of the site is never cut, the help under the settings has no empty title line.
  • Where a value comes from, said right: a value set by the group of the device reads group Pesa, no longer common settings; the others read site or local.

0.2.9 (2026-10-21)

  • Groups of devices, as folders of the management folder. config\groups\<group>\_group.conf holds the settings of a group (between common.conf and each device); the files of its devices sit next to it, so the folder a file is in is the group of the device, and moving the file moves the device. Devices with different accounts, or the same one, in as many groups as you like. The manager shows the devices in collapsible groups, creates and deletes groups, and moves a device to another group (its file moves in the share).
  • The devices as a tree, as in the Health Center: the site (your domain), its groups and the devices, each with the dot of its state. Selecting the site shows the settings of every device (moved here from the Settings page), a group its own (what is ticked is set there and wins from there down, the rest shows the value inherited from the site), a device its own. Drag a device onto a group, or right click; New group above the tree.
  • Health Center settings in tabs (Hyper-V, domain and desktops, SQL and files, devices and backups, checks), in a window of fixed size with Save always in sight. The updates of the manager are on the Updates page.
  • Fewer false problems in the Health Center: a former broker still named as fallback by some devices is no longer shown as a broker failing every sign-in, nor as missing in the permissions of the hosts; the time source of a server is not judged before the domain controllers are read.
  • A renamed device just gets its new name: no empty file of its own is left behind, and it stays in its group.
  • A faster manager. The vault opens in 0.2 s instead of 2.4 s after the access code (the PBKDF2 of Windows, the same keys); its C# is compiled once and kept, so it loads in half the time; and while the Health Center reads the servers it no longer stops the window when its page is not open.
  • 0.2.8 (hardware test, package list) was not published on its own: it is part of this release, with the new ISO.

0.2.8 (2026-10-21)

  • Hardware test. The live system tests the device at its first start, and any device does from Diagnostics (Hardware test): processor, memory, disk, graphics driver, missing firmware, kernel errors, network, DNS, clock, sound, USB, TPM, Secure Boot, FreeRDP with UDP, the broker and the management folder. Send to the OpenThinRDP project opens a ready-made hardware report on GitHub, sent with your own account; nothing in it identifies the device or the network (no name, address, MAC or serial number, checked by the tests).
  • The package list of every ISO (openthinrdp-<version>.packages.txt), name and version of each package.
  • New ISO: the licence (GPLv3), the folder from the domain and the hardware test from the first start (built as 0.2.9).

Unattended install, a separate entry of the boot menu, keeps the old behaviour for rollouts on known hardware.
  • FreeRDP: pull request #13608 unchanged, no patches of ours. The author took our two fixes into the pull request (ten SYN attempts, and the root cause of the false "stream is stuck" on lossy lines), which also removes a 1 s freeze at every wrap of the channel sequence under loss: with 70% of the packets lost the session now keeps 18-19 frames per second instead of 9-13.
  • Settings PIN salted and stretched (PBKDF2-SHA256, 600,000 iterations) when set from the manager; a PIN of 0.1.4 and earlier keeps working.
  • Docs: the devices' account needs write access to status\ only (management.md); replacing or revoking the release key through the update channel (SECURITY.md).
  • FreeRDP gets 20 s instead of 30 to bring a connection up: a broker that accepts the connection and then hangs costs this much on every attempt before the next broker is tried. Still above the 15 s a broker took to prepare a virtual machine.
  • The system tests (93) and a shell syntax check run in Debian 13 on every push and pull request (CI).

0.1.4 (2026-10-12)

  • The project moved to the OpenThinRDP organization: https://github.com/OpenThinRdp/openthinrdp, website https://openthinrdp.github.io/. The old addresses redirect, and devices already installed keep updating.

  • Security: FreeRDP 3.32.2, the security release of 2026-10-12, with the UDP transport (pull request #13608) on top. The USB fixes #13674, #13679 and #13618 are part of 3.32.2.

  • UDP holds on lossy lines. We found and fixed a bug in the UDP transport: after the channel sequence wrapped, a wrong elapsed time (an unsigned difference going below zero) made the client believe the stream had been stuck for ages, and it ended the connection within seconds whenever packets were being lost. Now the session keeps 20 frames per second with 50% of the packets lost and 9 with 70%, and still draws at 80%; TCP is down to 0.6 at 20%. The tunnel is also set up with ten attempts instead of four. Both fixes are proposed to FreeRDP in pull request #13608. See docs/udp.md.

  • FreeRDP gets 30 s instead of 9 to bring a connection up and to wait for the TCP connection beside the UDP tunnel (/timeout): a broker preparing a virtual machine in 15 s no longer makes the first attempt fail, and on a very lossy line the TCP connection is not given up while the UDP tunnel still carries the session.

  • Fix: no microphone in meetings with a webcam. A webcam was passed to Windows as a whole USB device, and Windows keeps the microphone of such a device in the console session: Teams and Zoom in the remote session found no microphone at all. Webcams and USB headsets now stay on the thin client: the camera goes through the RDP camera channel ([MS-RDPECAM]), the microphone and the speaker through the RDP audio channels. Devices plugged in during the session follow the same rule, and a webcam an earlier version had passed over USB is given back to the thin client by itself (its Linux drivers are attached again).

  • Updates installed during a session take effect when it is over: as soon as the device is back to the sign-in screen, or a new connection starts, the screen reloads with the new version (before: at the next start).

  • The mouse pointer on the kiosk screens (sign-in, progress, messages) hides while the mouse is still and comes back as soon as it moves; in the remote desktop it is Windows' own pointer as before.

  • Fix: a device moved to another management folder by MGMT_SHARE in the common settings went back to the folder of its image at the next report, and kept bouncing between the two.

0.1.3 (2026-10-12)

In production: this version runs a fleet of thin clients converted in place, updated from their management folder.

  • New screens for the user (GTK, full screen, on the background of the site): sign-in with the clock and date, information and settings small in the top right corner, power with Restart and Shut down bottom right, the web button bottom left; desktop start with a progress bar that follows the real steps (broker, redirection, desktop on screen); errors, no network, session open elsewhere, session taken over, end of session with a countdown. Settings, diagnostics and PIN stay simple dialogs (administrators only).
  • Software updates: a notice with the progress in the top right corner while one installs; Shut down during an update shows it full screen and switches off when it is done (before, it interrupted the install).
  • The boot screen always shows the picture and colors of the image (OpenThinRDP's, or yours when you build your own image); the picture of the management folder is the background of the sign-in screen, which is drawn again as soon as a new one arrives. In the manager the button is now Logo and background....
  • Devices still showing the provisional logo of 0.1.0 get the current one (only exact project pictures are replaced, never those of your own image).
  • FreeRDP: the USB fix for a client hanging on disconnect is now FreeRDP#13679 (by the FreeRDP maintainer, from our #13677); #13674 was approved.
  • Manager: a picture whose width already fit was not scaled to the height.
  • Day and month of the sign-in screen follow LANGUAGE, not the system locale.

0.1.2 (2026-10-12)

  • Fix: update packages always carry 755/644 modes. The 0.1.1 package was built with umask 002, and a device that installed it got a group-writable /etc, so sshd refused every key. Installing 0.1.2 repairs it. The 0.1.1 package was withdrawn; the 0.1.1 ISO was not affected.
  • The README links always point to the latest release.

0.1.1 (2026-10-12)

  • Security: no text consoles. Ctrl+Alt+F1..F12 and Ctrl+Alt+Backspace do nothing in the kiosk, no spare consoles with a login prompt, the kiosk account is locked. In 0.1.0 kiosk had no password: anybody at the keyboard could get a shell with Ctrl+Alt+F2. Devices updated from 0.1.0 are fixed too.
  • Secrets (Wi-Fi key, management folder password) are never printed back, only their hash.
  • Logo and boot image from the Windows manager, for every device or for one (config\branding\); the boot splash follows, also when only the colors change.
  • Diagnostics button (ℹ) on the sign-in form, without a PIN: network, brokers, time, management folder, events.
  • A new device names itself thinclient- + the last 6 digits of its MAC address.
  • Management folder account in the settings dialog and in the central settings (MGMT_USER, MGMT_PASSWORD).
  • MULTIMON=auto|off: one remote desktop over every monitor.
  • Certificate authorities of the site are trusted by the system too.
  • Settings labels with a colon (hh:mm, VID:PID) were cut short since 0.1.0.
  • README: direct connection to a Windows PC, what comes next.
